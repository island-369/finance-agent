## 1. 退出条件对照

| 退出条件 | 验证 |
| --- | --- |
| 断开前端不会丢任务 | 任务落库(runs 表)后由 Worker 独立领取执行;SSE 断开仅断流,`Last-Event-ID` 重连后从 run_events 精确补读(真实进程实测 seq=30 → 从 31 起) |
| 中断 Worker 后可按声明恢复 | 崩溃(requeue)保留引擎检查点与预算;再次领取以 `None` 输入续跑(已完成的工具调用不重复);预算沿用已消耗计数(§10.4,测试断言 2+3 次模型调用) |
| 旧 Worker 不能覆盖结果 | 终态写入校验 fencing token:失租旧 Worker 的 finish/update_budget 返回 0 行被拒(测试:旧 token 提交"旧"结果 → 新 Worker 结果保留) |
| 重复请求不会产生重复产物 | Idempotency-Key+摘要(同键同体重放、同键异体 409)+ `(run_id, kind)` 唯一约束;真实进程实测同键重放返回同一 run_id |
| 不可恢复场景有真实错误说明 | 尝试耗尽 → failed 且保留完整错误文本(`已达最大尝试次数(N): …`);模型装配失败 → 直接 failed 附真实原因 |

## 2. 架构与组件

```text
adapters/persistence/   models(runs/run_events/artifacts/idempotency_keys)
                        repository(领取/租约/fencing/幂等/终态同事务提交)
adapters/engines/deepagents/executor.py   run 行 → 引擎执行:事件逐条落库(实时 SSE)、
                        预算持久化、取消检查、崩溃恢复(invoke None)、HITL 恢复
interfaces/api/app.py   FastAPI:POST /v1/runs(202+幂等键)、GET 状态/产物、
                        cancel(幂等)、resume(approve/reject)、SSE(Last-Event-ID)、
                        /v1/skills、/v1/engines
worker/main.py          领取循环 + 周期续租 + 优雅退出;fa-worker --once 用于演示
interfaces/cli/db.py    fa-db upgrade
```

状态机(§6.3):`queued → running → validating → succeeded / completed_partial`,
另有 `waiting_input`(工具审批)→ resume → `queued`,`failed / cancelled`。
取消为标记位(`cancel_requested_at`),Worker 在每次模型/工具调用前检查。

## 3. 关键决策与如实记录

1. **领取 SQL 的方言分支**:SQLite 用 `UPDATE..WHERE id=(SELECT..) RETURNING`
   一次完成;PostgreSQL 用 `FOR UPDATE SKIP LOCKED`(compose 部署形态)。
   时间参数以与 ORM DATETIME 存储一致的字符串绑定(内部统一 UTC)。
2. **Alembic 暂缓**:当前唯一部署形态是全新建库,`fa-db upgrade` 用
   metadata 建表与迁移等价;Alembic 已在依赖中,首个 schema 变更(M4 建
   documents/chunks/metric_observations 表)时引入 migrations 目录。这是对
   设计 §17"建表与迁移"的部分实现,如实标注。
3. **引擎检查点仍为 SQLite 文件**(每 run 一个,`data/runtime/checkpoints/`);
   PostgreSQL 检查点命名空间(§10.2)留待部署验证——本机 Docker(colima)
   守护进程不可用,compose 环路未在本机实测,PostgreSQL 方言分支仅有代码
   审查级置信度。
4. **恢复失败重试策略**:执行失败按 attempt 重新排队;M0 发现的"失败恢复
   污染线程"通过"崩溃恢复一律 invoke(None)、审批恢复按挂起数构造决定"
   规避;若恢复仍失败则计入 attempt,耗尽后 failed(带真实错误)。
5. **同进程发现**:SQLite 文件被删除重建后,旧 Worker 持有已删除 inode 的
   连接会静默轮询空库(真实进程实测)。运维约束:重建库必须重启 Worker
   (PG 无此问题)。

## 4. 本机操作

```bash
uv run fa-db upgrade    # 建表(默认 SQLite data/runtime/app.sqlite)
uv run uvicorn finance_agent.interfaces.api.app:app --port 8010 &
uv run fa-worker &

curl -X POST localhost:8010/v1/runs -H 'Content-Type: application/json' \
     -H 'Idempotency-Key: demo-1' -d '{"objective":"…","entity_ids":["demo-company-a"]}'
curl localhost:8010/v1/runs/<id>            # 状态/预算/摘要
curl -N localhost:8010/v1/runs/<id>/events  # SSE(可加 Last-Event-ID)
curl localhost:8010/v1/runs/<id>/artifacts
```

Docker Compose(PostgreSQL + API + Worker):`docker compose up --build`
(需可用 Docker 守护进程与 .env 中的模型秘钥)。

## 5. 结果校验链与修复循环(2026-10-24 补充实现)

设计 §11 第 1–4 步与 §6.2 第 7 步的运行时落地(`application/result_validation.py`):

- **校验时机**:候选结果提交后、终态写入前(validating 状态);
- **校验内容**:引用存在性(obs/chk/docv/calc 必须来自本次运行工具输出,
  available_at ≤ as_of)、计算匹配、关键判断引用完整性(fact/inference 须带引用)、
  正文数字映射(启发式:观测值 元/万/亿/万亿 换算、计算值百分比含整数约数、
  同指标两观测的差/比/百分比推导、引用的证据原文中出现的数字;年份/日期/
  证据定位豁免);
- **修复循环**:可修复问题渲染为反馈消息追加进会话,模型重新提交,最多
  `result_repair_rounds`(默认 2)轮,计入预算;修复期间工具输出通过
  `runs.tool_trace` 跨 attempt 累积(审批场景多次恢复后 trace 完整);
- **终态语义**:全部通过 → succeeded;引用不存在等硬错误耗尽修复轮 →
  failed(确定性失败,不 requeue);仅剩数字映射问题 → completed_partial
  (quality_flags=["pending_review"],产物照常提交);
- **真实模型实测**:run-20261024-715d3e 走完 3 轮校验 + 2 轮修复
  (修复把可修复问题 21→13),最终 completed_partial;其结果经启发式
  改进(剔除引用 ID/日期/定位误报、证据原文匹配、约数取整)后离线复检
  完全通过——改进验证用真实数据,未重跑任务(§16.2 纪律)。
